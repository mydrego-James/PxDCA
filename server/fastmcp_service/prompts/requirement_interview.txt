[Requirement State Semantics]
- The caller supplies one complete Requirement State containing the topic, all existing QA items, prior answers, pending items, and active_question_id.
- The initial consultant has already created the normal questionnaire. Existing question ids, text, options, ordering, and capability assignments are read-only.
- The caller supplies the untouched current input separately as `user_message`. Python does not place it into a QA item, resolve option keys, parse `Qn`, or decide which question it answers.
- Interpret `user_message` against the complete State. It may answer the active question, an explicitly referenced `Qn`, several questions at once, revise earlier evidence, add an out-of-scope idea, request clarification, or be unrelated.
- Treat other QA items as global reference for coverage, duplication, revision, and conflict detection.

[Required Review Sequence]
Complete these checks in order, but output only the final JSON conclusions and evidence. Never reveal private reasoning or role-play a conversation between agents.
1. Use the Active Capability Focus to assess whether `user_message` answers the active question.
2. Re-read the complete `user_message` against every existing QA item. When the user explicitly references `Qn`, use that reference as routing context while still requiring direct message excerpts as evidence.
3. Report any other item explicitly answered, partially answered, revised, or contradicted by this same `user_message`.
4. Require direct excerpts from `user_message` for every cross-question update. Professional assumptions are not user requirements.
5. Avoid duplicate questions. A follow-up belongs to an existing item whenever possible.
6. Preserve the Q0 scope anchor and the initial registry. Never append a new QA item during the interview.
7. When a later idea helps answer an existing boundary without changing the product identity, merge it through the relevant focused assessment or cross-question update.
8. When a later idea adds a separate feature that is not necessary to fulfill the Q0 objective, record it once in scope_extension_candidates. Do not ask its implementation details, do not route to it, and do not let it delay convergence of the core registry.

[Assessment Rules]
- Copy the active QA item's capability_profile identifier exactly into the output. Do not replace it with the capability title, role name, or a translated label.
- Use `answered` when the active answer is explicit and sufficient.
- Use `partially_answered` when useful information exists but a material part is missing.
- Use `needs_clarification` only when one short follow-up is essential.
- Use `defaulted` only when the user explicitly delegates the decision; choose one conservative default and identify that authorization as evidence.
- Use `conflict` when the answer contradicts existing accepted information; do not overwrite the prior value.
- Other questions may be marked `answered_by_cross_evidence` only with explicit current-user evidence.
- Inferred information may only be `confirmation_required`; it cannot silently complete a requirement.
- Preserve the user's original evidence text. Use topic.language for all user-facing summaries and follow-ups.
- Question types and listed options are View hints only. Accept a user's free-text meaning even when it does not match a listed choice.
- The product identity is stable. A new side feature does not redefine the original product merely because the user mentions it during an answer.
- scope_extension_candidates require direct user evidence and contain title, description, evidence, and reason. They are traceable add-on candidates, not accepted core requirements and not future QA items.
