[Planning Rules]
- Analyze the complete seed request before creating questions.
- Use the user's language for every user-facing question, option, and summary. Keep JSON field names in English.
- Treat selected_profile as the caller-authorized document depth (`simple`, `professional`, or `consultant`), never as a capability profile.
- Read the selected_profile requirements from the authoritative depth-profile policy. The initial registry must cover every required dimension either as a seed-satisfied item or as a pending material boundary. Do not silently omit a required dimension.
- Extract every explicit fact already supplied and preserve the original user evidence.
- Create the complete material QA registry now with 3 to 15 project-specific foundation boundaries. Every material question must exist in qa_items in this first response; later turns fill answers into this registry instead of progressively inventing the normal questionnaire.
- Choose foundation boundaries that determine whether the requested product can be designed and delivered: purpose and success, actors or roles, core workflow, essential data and lifecycle, access or security, material integrations, deployment or operation, and non-functional acceptance as applicable to this topic. This is a relevance guide, not a mandatory checklist.
- Do not create cosmetic or low-impact implementation-detail questions such as text wording, ordinary colors, spacing, or decorative preferences unless the seed explicitly makes branding, accessibility, or visual fidelity a core acceptance constraint.
- Give every item a stable sequential question id `Q1` through `Qn`, plus display_order, dimension, policy_dimensions, capability_profile, target_fact, priority, status, complete question object, answer, assessment, and follow_ups. The id is part of your LLM output and is canonical; the Python caller will preserve it exactly and will not create or map display ids. Priority must be an integer from 1 through 10; 10 is highest.
- policy_dimensions is an array of exact keys from the selected depth profile's cumulative required list. One broad boundary may cover several keys. Across the complete registry, every required key must be covered at least once; this mapping is validated deterministically by MCP.
- Question options must be objects with stable numeric string keys (`1`, `2`, ...) and user-facing labels. Use an empty options array for fill-in questions.
- Choice options are concise decision directions, not a feature advertisement. Do not suggest unrelated add-ons merely because they are common for this product type. For sparse seeds, prefer architecture-level choices and a neutral `not decided` choice. Every View accepts a free-text answer even when options are present, so never force the user into the listed choices.
- Do not create an optional-feature shopping-list question. If interactivity is materially relevant but unspecified, distinguish only architectural classes such as display-only, visitor data submission, authenticated workflow, or a user-described need. Do not name comments, newsletters, social feeds, membership, commerce, or other side features unless the seed already mentions them.
- A generic `other` or `user-described need` option must be neutral and contain no parenthetical examples. Never use that option to introduce possible features, vendors, frameworks, hosting products, or implementation methods that are absent from the seed.
- Keep each boundary semantically coherent. Do not combine core product scope, content maintenance, authentication, and optional advanced functions into one choice list merely to reduce the registry size.
- A boundary mapped to `acceptance_criteria` must use `multi_choice` or `fill_in`, because independent acceptance conditions are not mutually exclusive. Phrase choices as observable outcomes or measurable constraints; avoid subjective superlatives such as perfect, extremely fast, attractive, modern, or high quality without a stated measure.
- PASS compatibility note: retain the preceding authoring preference for traceability, but `question.type` is only a View hint. Every question accepts free text, so a type mismatch must never invalidate an otherwise usable questionnaire.
- Use status `pending` with answer null and assessment null when information is missing.
- When the seed already resolves an item, use status `satisfied`; answer must be `{"raw":"exact seed excerpt","resolved_values":["..."],"normalized":"...","source_turn":0,"source_question_id":"Q1","resolution":"seed_explicit"}` and assessment must be `{"status":"satisfied","normalized_value":"...","evidence":["exact seed excerpt"],"reason_summary":"..."}`. Never use a bare string for answer or assessment.
- Create only questions that can materially change product scope, workflow, architecture direction, cost, security, deployment, or requirement completeness.
- Assign `capability_profile` using one exact capability id from the Available capability profiles JSON keys. Never write a display name, programming language, framework, vendor, or invented capability id into this field.
- Select capabilities by engineering responsibility or material domain boundary, not by implementation language. For example, Java, Python, C#, JavaScript, and specific frameworks are technology choices, not separate capabilities.
- Prefer broad capability coverage and do not mechanically split every application into frontend, backend, database, platform, and quality questions. Assign `frontend_engineer`, `backend_engineer`, `database_architect`, `platform_engineer`, or `quality_engineer` only when that boundary can materially change architecture, delivery, risk, or acceptance. A domain capability may own routine full-stack implications when those boundaries are not independently material.
- Put optional ideas only in advisory_suggestions. Advice is not a requirement unless the user explicitly adopts it.
- During initial discovery, keep advisory_suggestions empty unless the seed explicitly asks for recommendations. Do not introduce vendors, frameworks, hosting products, or implementation choices before the requirements justify them.
- Set active_question_id to the highest-value pending item. If every material item is already satisfied, set it to null and converged to true.
- The initial registry contains 3 to 15 material candidate boundaries, selected according to the seed's scope. This range is not a turn target: seed evidence and each later answer may satisfy several boundaries, so the number of questions actually shown to the user remains dynamic.
